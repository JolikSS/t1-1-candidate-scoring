# Правила парсера вакансий 2.1

## Вход и этапы

`parse_vacancy_bytes(file_name, content)` читает PDF/TXT и вызывает
`parse_vacancy_text(text, skill_catalog=None)`.

1. Проверка размера, кодировки или доступности текстового слоя PDF.
2. Очистка печатных колонтитулов и браузерных служебных строк; отсечение
   блока похожих вакансий. Общий модуль очистки резюме не изменяется.
3. Название: явная подпись должности, заголовок печатного экспорта либо
   подходящий заголовок роли. У печатного экспорта строка после «Обновлена … №»
   считается названием, с объединением продолжений. В неоднозначных случаях
   используются предупреждения общего механизма выбора названия.
   Продолжение останавливается перед разделом, контактом, пунктом списка,
   адресом с обозначением населённого пункта или известным началом описания
   обязанностей/компании. Скобки и разделители помогают сохранить переносы;
   продолжение со строчной буквы без этих признаков ограничено шестью словами.
   Незавершённые скобки или разделитель дают `possible_wrapped_title`.
4. Объединение переносов маркированных пунктов, незакрытых скобок и некоторых
   продолжений строк. Новый раздел или новый маркер начинает отдельный пункт.
5. Разделение требований, желательных навыков, обязанностей, условий и контекста.
6. Поиск известных навыков общим механизмом сопоставления и их классификация.

`description` содержит только требования, желательные навыки, обязанности и
профессиональный контекст. Условия оформления, льготы, контакты, миссия и
ценности компании в него не включаются. Явные заголовки стека, квалификационного
уровня или следующего профессионального раздела возобновляют сбор даже после
условий/рекламы. «Как будем работать» относится к описанию рабочего процесса:
в нём могут находиться задачи прототипа, а не только условия занятости.
«График работы» и «Тип занятости» открывают отдельный непрофессиональный раздел.

Контакты и явно обозначенные строки оформления/льгот очищаются **до** объединения
переносов. Удалённая строка разрывает продолжение пункта списка, чтобы отрицание
или маркер желательности не переносились через неё. Поддерживаются также
маркеры `·`, `•`, `●`, `*`, тире и нумерованные пункты.

Граница раздела распознаётся по полной строке заголовка или по заголовку с
разделителем перед содержимым. Фраза «Требования к документации уточняет команда»
не считается заголовком требований. Полный список в `SECTION_ALIASES` и
`HEADING_VARIANTS` файла `vacancy_parser.py`.

## Навыки

Источники `required_skills` и `preferred_skills` — разделы требований и
желательных навыков. Условия, описание компании, стек команды и обязанности
сами по себе не создают обязательных навыков.

| Формулировка в требованиях | Обязательные | Желательные |
|---|---|---|
| Python; Docker будет большим плюсом | Python | Docker |
| Python, SQL будут плюсом | — | Python, SQL |
| Python, желательно Docker | Python | Docker |
| Spark, dbt (большой плюс), Airflow | Spark, Airflow | dbt |
| Docker и SQL не требуются | — | — |

Область маркера ограничивается предложением, частью с точкой с запятой или
противопоставлением. В списках поддерживаются маркеры перед списком и после него.
Маркер внутри скобок одного элемента не меняет соседние элементы.
Обязательное упоминание выше желательного. Противоречие «обязателен» /
«не требуется» исключает навык из обеих итоговых групп и создаёт предупреждение.
Отрицания опыта обрабатываются также общим сопоставлением навыков проекта.

Учитываются границы слов и составных названий: Java не извлекается из JavaScript,
JavaScript — из Node.js, SQL — из SQLAlchemy. Алиасы находятся в общем
`scorer/expression_catalog.py`. Для Go используются точное Golang и явные
языковые контексты: английский глагол go сам по себе не считается навыком.

Неизвестные слова остаются в текстовых полях. Каталог можно расширить явно.
Сложные альтернативы «хотя бы один из …» не преобразуются в логические условия.

## Контракт результата

`ParsedVacancy` сохраняет поля `title`, `requirements`, `responsibilities`,
`description`, `required_skills`, `preferred_skills`, `parse_details`.
`to_dict()` возвращает JSON-совместимый словарь.
`parse_details` включает версии правил и справочника, `title_selection`,
`skill_evidence` (навык, категория, раздел, фрагмент, контекст, правило) и `warnings`.
В `title_selection` сохраняются `line_number` и `end_line_number` — первая и
последняя строки названия в очищенном списке строк. Это позволяет исключить
все части перенесённого названия из резервного описания.

Для незнакомой структуры сохраняется резервное описание с `unstructured_text`,
без автоматического превращения всех упоминаний в обязательные навыки.
Этот путь использует те же правила очистки и границы разделов: исключённые
условия и контакты не возвращаются в текст при пустом основном описании.
Если после очистки профессионального текста нет, возвращается пустое описание
с `empty_professional_text`. Неизвестные профессиональные слова сохраняются.
При отсутствии названия используется «Вакансия» с предупреждением.
Отсутствующие требования и обязанности обозначаются предупреждениями.
Пределы полей: требования и обязанности по 12 000 символов, описание 20 000.
Обрезание сопровождается `truncated:<поле>`; классификация использует весь
разобранный текст требований, а не только обрезанное поле.

## Пакетный запуск и интеграция

`python -m Parser.parse_vacancies INPUT -o OUTPUT.json` поддерживает файл,
рекурсивную папку и ZIP. Лимиты: 20 МиБ на документ, 100 страниц PDF,
1 000 000 символов извлечённого текста, 200 документов / 100 МиБ прочитанных
документов на пакет. Лимиты общие для одного запуска; содержимое ZIP не
извлекается на диск. Ошибки отдельных документов сохраняются рядом с успешными
результатами. При превышении общего лимита обработка пакета прекращается,
предыдущие результаты сохраняются. Дубликаты определяются по SHA-256 байтов.

Существующее API сохраняет дополнительные поля вакансии через
`api/services/documents.py`. В нём действуют также собственные настройки
ограничений из `api/config.py`. Автоматического изменения старых записей нет.

## Границы и проверка

Парсер работает локально, не обращается к hh.ru/SuperJob и не требует LLM/GPU.
OCR и DOCX не реализованы. PDF с необычным порядком текстового слоя и неизвестные
формулировки могут потребовать ручной корректировки.
Правила не обеспечивают полного понимания произвольного естественного языка.
Короткая фраза со строчной буквы без явных признаков описания ещё может быть
неоднозначной. Список начал описания расширяется по воспроизводимым примерам;
новое правило не гарантирует распознавание любой формулировки.
Очистка рекламы и условий также основана на явных заголовках и конечном наборе
маркеров. При смешении требований и льгот внутри одного предложения или при
неизвестном заголовке результат требует проверки. Само упоминание технологии
в условиях не становится требованием или основанием сохранять весь блок.
Результат испытания на предоставленном корпусе — в `VACANCY_PARSER.md`.
