# Приёмка, бенчмарк и доступность

## Технические проверки

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt
python tools/check_backend.py
```

Команда проверяет стиль и форматирование изменённых компонентов и запускает
все unittest. `.github/workflows/backend.yml` выполняет эти проверки на
Python 3.10/3.12, затем проверяет настоящие MongoDB и Neo4j. Результат публикации
workflow смотрите в Checks/Actions: первый запуск из форка может требовать
разрешения владельца. Конфигурация CI сама по себе не подтверждает успешный прогон.

Для локальной проверки настоящего HTTP API:

```bash
python tools/verify_backend.py --mongo-uri mongodb://127.0.0.1:27017 --batch-size 500 --long-pages 100
python tools/verify_backend.py --mongo-uri mongodb://127.0.0.1:27017 --neo4j-uri bolt://127.0.0.1:7687 --batch-size 100
```

Для графового сценария нужен отдельный тестовый Neo4j; пароль берётся из
NEO4J_PASSWORD в окружении или локальном .env. Скрипт создаёт случайную временную
MongoDB и запускает собственный Uvicorn. Проверяются конкурентные загрузки,
пакеты PDF/TXT, многостраничный PDF, оба профиля нового API, старый API,
совпадение рейтинга HTTP/MongoDB/Neo4j, воспроизведение по снимкам, HR,
сохранность истории после перезапуска и обнаружение остановленного сервера.
После проверки свой сервер и временная MongoDB удаляются. В графе удаляются
собственные узлы и новые связанные навыки, если они больше не используются;
ограничения уникальности остаются.

В `tests/acceptance_cases.py` заданы технические примеры для 20 направлений:
ИТ, бухгалтерии, продаж, маркетинга, HR, логистики, закупок, права, дизайна,
строительства, здравоохранения, образования, производства, гостиничного дела
и сельского хозяйства. Они используют вручную заданные требования и синтетические
резюме. Это проверяет общий API, но не полноту автоматического парсинга и качество
подбора реальных документов всех профессий. Автоматический каталог преимущественно ИТ.

## Профили текста

По умолчанию новый `/scoring-runs` использует `feature_profile=lemmas-ru-en-v2`
и версию `weighted-coverage-tfidf-lemma-v2`. Русский и английский остаточный текст
обрабатывается словарным лемматизатором simplemma 1.2.0. Словари входят в пакет;
внешние модели и отдельные процессы не нужны. Известные технологии остаются целыми
признаками, отрицательные упоминания маскируются до лемматизации. Неизвестные слова
сохраняются. Контекстная неоднозначность словарём полностью не решается.

`feature_profile=expressions-v1` возвращает прежнее поведение нового API
с версией `weighted-coverage-tfidf-v1`. Старый `/score` продолжает использовать
исходную подготовку без лемматизации. История не пересчитывается.
Параметры запуска содержат профиль, каталог и версии Python, NumPy, sklearn, simplemma.

## Размеченный датасет

Пример формата: `docs/examples/benchmark.synthetic.json`. Он маленький и явно
синтетический; использовать его для подтверждения качества и выбора рабочих весов
нельзя. Приватные наборы храните в `data/evaluation/`, отчёты — в `artifacts/`.
Оба каталога исключены из Git.

Один JSON до 64 МиБ содержит:

| Поле | Значение |
|---|---|
| schema_version | candidate-benchmark-v1 |
| source | real или synthetic — объявленное автором происхождение |
| vacancies | id, title, domain и поля вакансии, включая required_skills/critical_skills |
| resumes | resume_id, anonymized_text и подготовленные поля резюме |
| judgments | vacancy_id, resume_id, label (целое 0/1), split |

1 означает релевантность по экспертной разметке, 0 — нерелевантность.
Split: train, validation или test. Повторные ID документов, повторные пары,
неизвестные ссылки и попадание одного ID в разные части отклоняются.
Автор должен также исключить одинаковые тексты под разными ID и проверить разметку.

```bash
python tools/evaluate_scoring.py data/evaluation/dataset.json --audit-only --require-tz-dataset
```

Аудит считает только размеченные документы и проверяет 50 уникальных резюме,
50 положительных и 50 отрицательных пар, 20 объявленных направлений и оба класса
в validation и test. По 50 пар каждого класса — консервативный критерий для
неоднозначной фразы ТЗ «не менее 50 позитивных и негативных пар».
Код завершения 2 означает невыполнение критериев состава. Синтетический набор
всегда получает dataset_requirements_met=false. Поле source=real является
декларацией: скрипт не удостоверяет происхождение документов и истинность меток.

## Метрики и подбор весов

```bash
python tools/evaluate_scoring.py docs/examples/benchmark.synthetic.json --calibrate
python tools/evaluate_scoring.py data/evaluation/dataset.json --calibrate --output artifacts/calibration.json
python tools/evaluate_scoring.py data/evaluation/dataset.json --split test --coverage-weight 0.7 --critical-multiplier 2 --threshold 50 --output artifacts/test.json
```

Вывод содержит SHA-256 набора, версии зависимостей, аудит, precision, recall, F1,
ROC-AUC, MAP, nDCG@k и precision@k, включая разрез по направлениям. Отдельно
подсчитываются отрицательные пары с Score >=95 как диагностический контроль
оценок, близких к 100. Исходные тексты и индивидуальные оценки кандидатов
в отчёт не включаются. Score не является вероятностью; порог нужен для метрик.

Оцениваются только размеченные кандидаты каждой вакансии. Неоценённые пары
не считаются отрицательными. Отчёт описывает выбранный набор кандидатов и не
заменяет оценку поиска по всему корпусу. Знаменатель precision@k — min(k, число
размеченных кандидатов). MAP и nDCG усредняются по запросам с положительными
метками; количество остальных запросов указано отдельно. ROC-AUC при одном классе — null.

Подбор перебирает веса покрытия 0.25, 0.5, 0.7, 0.9, множители критических навыков
1.5, 2, 3 и пороги 25, 50, 75. Выбор делается по F1 на validation, затем nDCG@k,
при равенстве — по стабильному порядку параметров. После выбора один раз
вычисляются метрики test с выбранными параметрами. Метки test не используются
для выбора. Если после просмотра test алгоритм изменяется, нужен новый отложенный набор.

По умолчанию `--corpus-policy split`: IDF и каталог строятся только по документам
соответствующей части. `--corpus-policy shared` явно включает тексты всех частей
в общий индекс, в том числе отложенные тексты. Эти режимы нельзя сравнивать без
оговорки. Часть train доступна для отдельной оценки; классификатор на её метках
не обучается. Весовые коэффициенты подбираются на validation.

Инструмент не меняет настройки API. После проверки на реальных данных выбранные
веса можно передать в запросе или настройках SCORING_COVERAGE_WEIGHT и
SCORING_CRITICAL_MULTIPLIER. Идеальные метрики на синтетическом примере не
подтверждают качество, а подобранные на нём веса не предназначены для приложения.

## Мониторинг доступности

```bash
python tools/monitor_availability.py --url http://127.0.0.1:8000/health --duration 86400 --interval 30 --required-window 86400 --samples artifacts/readiness-day1.jsonl --report artifacts/readiness-day1.json
```

Проверяется HTTP 200 и JSON status=ok. После каждого запроса записывается JSONL.
Файл образцов создаётся новым, чтобы окна не смешивались; Ctrl+C завершает
наблюдение с отчётом по фактическому времени. URL, тело ответа и текст исключений
со строками подключения в образцы не записываются.

Доступность оценивается по состоянию между пробами. Разрыв более двух интервалов
считается неизвестным временем. Для полного окна нужны минимум две пробы,
длительность >=required-window и покрытие наблюдением >=99%. Иначе meets_target=null,
даже если все короткие пробы успешны. После полного окна доступность <95%
даёт meets_target=false и код завершения 1.

Пересчёт сохранённого журнала:

```bash
python tools/monitor_availability.py --samples artifacts/readiness-day1.jsonl --summarize --elapsed 86400 --interval 30 --required-window 86400 --report artifacts/readiness-recalculated.json
```

Elapsed — действительная длительность окна, включая периоды без проб. Если её
не указать, окно заканчивается последним сохранённым наблюдением. Пробы должны
иметь возрастающее конечное elapsed_seconds и корректные ok/latency_seconds.
Точность оценки ограничена интервалом: короткий сбой между пробами может остаться
незамеченным. Один день — начальная настройка; период и целевую среду надо согласовать.

## Оставшиеся условия приёмки

Нужны реальные документы с экспертной разметкой, оценка качества и калибровка
на них, замеры на настоящих длинных PDF и наблюдение доступности в целевой среде.
Переключение Streamlit на новый API, добавление HR и общего Score относится
к интеграции фронтенда.
