# Backend API v4

## Запуск

Python 3.10+, MongoDB 8.0, зависимости из `requirements.txt`.
Для команд `docker compose` нужен установленный Compose plugin.
При уже запущенной MongoDB можно сразу запускать Uvicorn.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env
docker compose up -d mongo
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

В Windows активация: `.venv\Scripts\activate`, копирование настроек:
`copy .env.example .env`. В IDE можно выбрать интерпретатор `.venv` и запустить
`run_project.py`, который подготовит БД, загрузит отсутствующие документы из
локальных архивов и запустит API со Streamlit. Остановка: `stop_project.py`.

Документация запросов и ответов: `http://127.0.0.1:8000/docs`.
OpenAPI: `/openapi.json`. `GET /health/live` проверяет процесс,
`GET /health` — готовность MongoDB. Неудачное подключение при старте оставляет
процесс доступным для диагностики с readiness 503; после исправления настроек
нужно перезапустить API. Временные ошибки уже подключённой MongoDB допускают
повтор запросов после восстановления соединения.

## Состав и ответственность

`api/main.py` создаёт приложение и сохраняет совместимый API v3 для Streamlit.
`api/routers/backend.py` содержит маршруты управления документами, расчётами и HR.
`api/schemas.py` задаёт входные и выходные модели. `api/config.py` проверяет настройки.
`api/services/documents.py` ограничивает загрузки и вызывает существующий Parser;
`api/services/scoring.py` собирает корпус, вызывает Scorer и сохраняет историю.
`db/mongo_store.py` отвечает за MongoDB, `db/graph_store.py` — за дополнительный граф.

Новые расчёты используют `scorer/weighted_ranking.py`, извлечение навыков — общий
каталог, алиасы и правила отрицаний в `scorer`. Парсер документов и TF-IDF
сохраняются как отдельные компоненты проекта. Новый профиль `lemmas-ru-en-v2`
добавляет словарную лемматизацию русского и английского остаточного текста.
Предыдущий `expressions-v1` доступен явно и сохраняется в старом `/score`.
Инструменты приёмки и бенчмарка: [ACCEPTANCE.md](ACCEPTANCE.md).

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health`, `/health/live` | Готовность БД и состояние процесса |
| POST | `/vacancies` | Создать вакансию вручную; занятый ID возвращает 409 |
| GET | `/vacancies` | Список вакансий, совместимый со Streamlit |
| POST | `/vacancies/upload` | Загрузить PDF/TXT или ZIP вакансий |
| GET, PATCH | `/vacancies/{id}` | Получить или изменить вакансию |
| POST | `/resumes/upload` | Независимая загрузка PDF/TXT или ZIP резюме |
| GET | `/resumes` | Страница резюме и общее число подходящих записей |
| GET, PATCH | `/resumes/{id}` | Документ и переключение `hidden` |
| GET | `/resumes/{id}/text` | Подготовленный профессиональный текст |
| GET | `/resumes/{id}/text?source=true` | Исходный извлечённый текст |
| POST | `/scoring-runs` | Новый расчёт итогового Score |
| GET | `/scoring-runs` | История; фильтр `vacancy_id` |
| GET | `/scoring-runs/{id}` | Сохранённые результаты и параметры |
| GET | `/scoring-runs/{id}/inputs/{kind}/{document_id}` | Снимок входа; kind: resume/vacancy |
| POST, GET | `/feedback` | Записать решение HR или получить историю |
| GET | `/scoring-runs/{id}/feedback/{resume_id}` | Последнее решение HR по кандидату в расчёте |
| GET | `/feedback/export` | Последние решения по каждой паре расчёт/резюме |
| POST | `/score` | Совместимый расчёт покрытия навыков, API v3 |
| GET | `/vacancies/{id}/results` | Последние сохранённые результаты без пересортировки |

Страницы `/resumes`, `/scoring-runs`, `/feedback`, `/feedback/export` принимают
`offset >= 0`, `1 <= limit <= 500`, по умолчанию 0 и 100. Резюме сортируются по ID,
история и решения — от новых к старым. `/resumes` принимает `include_hidden=true`.
`/feedback` поддерживает фильтры `run_id`, `resume_id`, `vacancy_id`.

## Пример рабочего сценария

1. `POST /vacancies`, JSON:

```json
{
  "id": "vacancy-1",
  "title": "Python backend developer",
  "description": "Разработка REST API",
  "requirements": "Python, Docker, PostgreSQL",
  "required_skills": ["Python", "Docker", "PostgreSQL"],
  "preferred_skills": ["Redis"],
  "critical_skills": ["Python"]
}
```

Критические навыки должны входить в обязательные с учётом алиасов.
Списки нормализуются и очищаются от канонических повторов. Название и навыки
не могут состоять из пробелов. Неизвестные поля JSON отклоняются.
PATCH проверяет итоговую вакансию, поэтому удаление обязательного навыка требует
одновременно убрать его из `critical_skills`. `null` и пустой PATCH отклоняются.

2. `POST /resumes/upload`, multipart, повторяемое поле `files`:

```bash
curl -F 'files=@resumes.zip' http://127.0.0.1:8000/resumes/upload
```

Ответ содержит `resumes`, `count`, `errors`. Успешные документы остаются в БД,
даже если часть пакета прочитать нельзя. Повторные загрузки возвращают прежние ID.
Поле `count` — число уникальных документов текущего пакета.

3. `POST /scoring-runs`, JSON:

```json
{
  "vacancy_id": "vacancy-1",
  "coverage_weight": 0.7,
  "critical_multiplier": 2,
  "feature_profile": "lemmas-ru-en-v2"
}
```

Без `resume_ids` оценивается весь активный корпус, до лимита кандидатов.
Для подмножества передайте непустой массив уникальных ID. Отсутствующие,
скрытые или не имеющие профессионального текста резюме дают 422.
TF-IDF в обоих случаях обучается на полном активном корпусе и всех сохранённых
вакансиях. Выбор подмножества не меняет IDF при неизменном корпусе.

Ответ 201 содержит `run_id`, `vacancy_id`, `vacancy_title`, `created_at`,
`ranking_version`, `parameters`, `corpus`, `results`, `resume_count`,
`duration_seconds`, `status=completed`.

4. `POST /feedback`, JSON:

```json
{
  "run_id": "ID_ИЗ_ОТВЕТА",
  "resume_id": "ID_ИЗ_РЕЗУЛЬТАТА",
  "label": "relevant",
  "reviewer": "hr-1",
  "comment": "Подходит по обязательным навыкам",
  "event_id": "hr-action-1"
}
```

Метки: `relevant` — релевантен, `irrelevant` — нерелевантен.
Резюме должно участвовать в указанном расчёте. Каждый новый `event_id` добавляет
событие. Повтор того же ID и содержимого возвращает прежнее событие с исходным
временем. Другое содержимое с занятым ID даёт 409. Без ID сервер создаёт UUID.
Изменение решения записывается новым событием; старое остаётся в истории.
`reviewer` — введённая метка, а не подтверждённая учётная запись пользователя.

Экспорт берёт последнее решение для каждой пары `run_id/resume_id`.
`include_text=true` добавляет подготовленные снимки вакансии и резюме из расчёта.
Исходный текст, комментарии и идентификатор проверяющего в экспорт не включаются.
Для старых расчётов без снимков поля документов будут `null`.
Автоматическое переобучение по решениям HR не запускается.

## Формула и версии

Для обязательного навыка вес равен 1, для критического — `critical_multiplier`.

```text
coverage = 100 × сумма весов найденных навыков / сумма весов обязательных навыков
Score = coverage_weight × coverage + (1 − coverage_weight) × text_similarity
```

`text_similarity` — косинусное сходство TF-IDF на шкале 0..100.
`0 <= coverage_weight <= 1`, `1 < critical_multiplier <= 100`.
Начальные значения 0.7 и 2 являются настройками для последующей калибровки,
а не коэффициентами, подтверждёнными разметкой. Желаемые навыки участвуют в
текстовом представлении вакансии, но не в покрытии обязательных требований.

При отсутствии обязательных навыков `skill_coverage=null`, Score равен TF-IDF.
Отсутствующий TF-IDF остаётся `null` и в сумме вносит ноль без перераспределения веса.
Score и покрытие округляются до четырёх знаков. Порядок: итоговый Score по убыванию,
затем ID по возрастанию. Шкала 0..100 не является вероятностью пригодности.

Версия нового расчёта по умолчанию: `weighted-coverage-tfidf-lemma-v2`.
При `feature_profile=expressions-v1` используется `weighted-coverage-tfidf-v1`.
Строка результата содержит ID, анонимную метку кандидата, тип и номер документа,
`score`, `skill_coverage`, `text_similarity`, найденные/отсутствующие обязательные
и критические навыки и `ranking_version`.

`POST /score` сохраняет `coverage-tfidf-id-v1`: `score` означает обычное покрытие,
порядок — покрытие, TF-IDF, ID. Это требуется действующему Streamlit, где столбец
подписан «Покрытие навыков». Для итогового Score, критических навыков и новых
элементов интерфейса фронтенду нужно использовать `/scoring-runs` и `/feedback`.
Сохранённая история не пересчитывается. Исторические записи без версии — `legacy`.
Записи до появления `run_id` остаются доступны через последний результат вакансии;
их ID автоматически не мигрируются.

## Хранение и воспроизводимость

| Коллекция | Содержимое |
|---|---|
| vacancies | Текущие вакансии и результат парсинга |
| resumes | Подготовленные резюме, навыки, hash и hidden |
| resume_sources | Исходный извлечённый текст отдельно от списочных ответов |
| scoring_runs | Завершённые расчёты, параметры и рейтинг |
| scoring_inputs | Неизменяемые документы полного корпуса на момент расчёта |
| feedback | Неизменяемые события HR |

Уникальные индексы защищают ID вакансий и резюме, хеши исходных файлов,
ID расчётов, источников, снимков и событий HR. Для run_id индекс частичный,
чтобы старые записи без этого поля не мешали запуску. MongoDB хранит время UTC
с точностью до миллисекунд; первый ответ HR также читается из сохранённой записи.

В новом расчёте навыки извлекаются на копиях прочитанных документов.
Сохранённые резюме не переразбираются и не перезаписываются во время расчёта.
Снимки исключают сырой текст и личные поля, сохраняют фактически использованные
поля сравнения. Манифест корпуса содержит ID и SHA-256 каждого снимка;
параметры — каталог, версии признаков, профиль, версии зависимостей и коэффициенты. Строки кандидатов содержат
ID подмножества. Это позволяет повторить расчёт в том же окружении зависимостей.

Каждый входной документ хранится отдельно из-за ограничения размера одного BSON.
История публикуется после записи всех снимков. Общей транзакции между коллекциями
и MongoDB/Neo4j нет: ошибка может оставить неполные снимки без успешного расчёта;
они не отображаются в истории API. При потере ответа после успешной записи
повтор POST расчёта создаст новый `run_id`; первый можно найти в истории.

Предзагрузка пропускает существующие вакансии и сохраняет ручные правки.
Явный повторный `/vacancies/upload` обновляет разбор и сбрасывает
`critical_skills`: их нужно заново отметить через PATCH.
Повтор исходного резюме возвращает сохранённый разбор. Если запись исходного
текста прервалась, явная повторная загрузка восстанавливает источник без переразбора.

## Ограничения и ошибки

По умолчанию: 500 документов/кандидатов в пакете, 20 МиБ на исходный файл,
512 МиБ на распакованный пакет и суммарные ZIP, 2 МиБ на извлечённый текст.
HTTP-запрос ограничен размером пакета плюс 2 МиБ на multipart-заголовки.
Архивы читаются в памяти по ограниченным потокам; имена файлов не используются
как пути и не сохраняются. Вложенные ZIP не распаковываются.

Защищённые PDF, пустые файлы и сканы без текстового слоя дают ошибки документов;
OCR не выполняется. Превышение общего лимита даёт 413 и не запускает импорт пакета.
После начала импорта сбой БД может оставить часть корректно сохранённых документов;
повтор загрузки безопасен благодаря хешам. Ошибки БД и расчёта дают 503,
отсутствующие ресурсы — 404, некорректные данные — 422, конфликты — 409.
Ошибки имеют поле `detail`; при частичном успехе загрузки — `errors`.

Одновременно выполняется до `MAX_PARALLEL_SCORES` расчётов на процесс,
по умолчанию один. Перегрузка даёт 429 с `Retry-After: 5`.
Лимит действует и на старый, и на новый API. Запуск рассчитан на один worker;
при нескольких процессах каждый имеет свой лимит, общей очереди задач нет.

Исходный текст может содержать личные данные и доступен только по явному запросу
`source=true` с `Cache-Control: no-store`. API предназначен для локального запуска
на 127.0.0.1 в рамках учебного проекта; пользовательская авторизация не добавляется.
Подготовка текста остаётся эвристической. Старые источники без исходного текста
дают 404; подготовленный текст доступен. Документы, токены и строки подключения
не записываются в сообщения ошибок приложения. Автоматические JSON-экспорты API
и предзагрузки включаются только через `EXPORT_ANONYMIZED_JSON=true`.

## Дополнительный Neo4j

По умолчанию `NEO4J_ENABLED=false`, MongoDB достаточно для всех новых сценариев.
Для графа задайте пароль, включите настройку и запустите:

```bash
docker compose --profile graph up -d neo4j
```

Новый расчёт сначала сохраняется в MongoDB, затем зеркалирует рейтинг,
требования и снимки навыков в Neo4j. Ошибка зеркалирования логируется и не отменяет
результат MongoDB; автоматической очереди повторов зеркалирования нет.
Для совместимого `/score` доступный включённый граф сохраняет прежнюю роль:
ошибка его ранжирования возвращает 503. При отсутствии подключения используется
такое же правило сортировки в Python. Существующие графовые данные не удаляются.

## Проверки

```bash
python -m unittest discover -s tests -v
python tools/check_backend.py
python tools/verify_backend.py --mongo-uri mongodb://127.0.0.1:27017
```

`verify_backend.py` запускает настоящий Uvicorn, создаёт БД со случайным тестовым
именем, проверяет конкурентную загрузку PDF, пакет из 100 PDF/TXT, воспроизведение
рейтинга, историю, HR, API v3, 20 технических направлений и перезапуск API.
`--neo4j-uri` включает проверку настоящего графа, `--long-pages` задаёт размер
многостраничного PDF. Затем скрипт останавливает свой сервер и удаляет только
свою тестовую БД. Локальные запросы обходят системный HTTP-прокси. Для проверки
пакета из 500 документов: `--batch-size 500`.

Проверка на пользовательских архивах: `tools/verify_pipeline.py`; она изменяет
настроенную рабочую БД и историю и выполняется отдельно.
Тесты на коротких технических документах проверяют работоспособность и контрольный
нерелевантный пример. Они не доказывают качество на 20 направлениях, выполнение
нормативов на реальных длинных PDF или доступность 95%. Для проверки качества и
калибровки нужен согласованный набор реальных размеченных пар и отдельный бенчмарк.
