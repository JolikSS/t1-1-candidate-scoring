# Единый рейтинг TF-IDF и cosine

Активная версия: `corpus-tfidf-cosine-v3`.
Оба маршрута `/scoring-runs` и `/score` используют этот алгоритм.

## Формула и порядок

`score = text_similarity = 100 * cosine(tfidf(resume), tfidf(vacancy))`.

Используется один `TfidfVectorizer.fit_transform` на весь корпус расчёта.
Параметры: `sublinear_tf=True`, `smooth_idf=True`, `norm="l2"`,
`min_df=1`, `max_df=1.0`, `lowercase=False`, `token_pattern=None`.
Анализатор — `ProfessionalAnalyzer` с общим каталогом технологий.
TF = `1 + ln(count)`; IDF = `ln((1 + N)/(1 + df)) + 1`.

Сортировка: сначала кандидаты с численной оценкой, по убыванию **неокруглённого**
Score; при точном равенстве — `resume_id` по возрастанию.
Затем неоценённые кандидаты по ID. Допуск для объединения близких оценок не применяется.
Для защиты от погрешности вычисления косинуса значение ограничивается диапазоном
0..100. API и MongoDB сохраняют полную точность float; Streamlit округляет до двух знаков.
Внешний потребитель должен сохранять порядок API и округлять только отображение.

Покрытие навыков, критические навыки, их множители и смесь 70/30 не участвуют
в формуле и сортировке. `matched_skills`/`missing_skills` служат пояснением.
Параметры `coverage_weight` и `critical_multiplier` удалены из запроса:
сервер отклоняет их с HTTP 422. Переменные окружения с этими весами больше не читаются.

## Корпус и подготовка

В HTTP-сценарии корпус включает все сохранённые вакансии и все нескрытые резюме,
в том числе документы без признаков. Выбор `resume_ids` ограничивает выдачу,
но не меняет корпус IDF. Текущие документы включаются однократно по паре
«тип документа, ID»; одинаковый текст под разными ID считается разными документами.
При работе без ID идентичность определяется подготовленным текстом.

Сохранена существующая подготовка документов (`text_similarity.py`):

| Документ | Поля и частотное усиление |
|---|---|
| Вакансия | title ×3, required_skills ×3, preferred_skills ×1, requirements ×2, responsibilities ×1, description ×1 |
| Резюме | title ×3, skills ×3, experience ×2, education ×1, anonymized_text ×1 |

Это повторение текста перед логарифмическим TF, а не дополнительный балл.
Пересекающиеся поля могут повторно включать одно содержание.
Критичность навыка на подготовку текста не влияет.

Общий каталог — базовый словарь и skills/required_skills/preferred_skills корпуса.
Алиасы становятся целыми `skill:...`, действия — `activity:...`, остаточные слова
и пары — `word:...` и `phrase:...`. Известные отрицательные упоминания маскируются.
По умолчанию HTTP использует `lemmas-ru-en-v2`; `/scoring-runs` также допускает
`expressions-v1`. Формула одинакова, профиль фиксируется в параметрах прогона.
Низкоуровневые функции сохраняют прежний default `expressions-v1`:
для повторения HTTP нужно явно передать сохранённый профиль.

В обоих API сохраняются снимки всего корпуса, профиль, каталог, версии библиотек
и хеши. Изменение корпуса меняет IDF и может изменить баллы даже неизменной пары.
Для сравнения версий алгоритма нужно фиксировать входы, профиль и зависимости.

## Нулевое сходство и отсутствие оценки

* Вакансия без признаков после подготовки — `EmptyVacancyError`, HTTP 422.
  Это включает пустые строки, пунктуацию, стоп-слова и чистые числа.
* Нулевой вектор резюме — `score: null`, `text_similarity: null`,
  `status: "insufficient_text"` («Недостаточно текста»).
* Ненулевой вектор без общих признаков с вакансией — численный `0`, `status: "scored"`.
* Проверяется весь подготовленный документ: даже при пустом основном тексте
  должность, опыт или навыки могут дать признаки.

Правила загрузки не меняются: полностью непригодный исходный файл может быть
отклонён парсером до скоринга. Уже сохранённые пустые резюме не исчезают из расчёта.

## Независимое воспроизведение

`fit_corpus_tfidf` открывает подготовленные строки, общий каталог и индексы.
Для проверки можно построить **новый** векторизатор:

```python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
from scorer.text_similarity import fit_corpus_tfidf
from scorer.tfidf_features import ProfessionalAnalyzer

fitted = fit_corpus_tfidf(candidates, vacancy, resumes, vacancies,
                        profile="lemmas-ru-en-v2")
vectorizer = TfidfVectorizer(
    analyzer=ProfessionalAnalyzer(fitted.catalog, "lemmas-ru-en-v2"),
    token_pattern=None, lowercase=False, sublinear_tf=True,
    smooth_idf=True, norm="l2", min_df=1, max_df=1.0,
)
matrix = vectorizer.fit_transform(fitted.documents)
scores = cosine_similarity(
    matrix[fitted.candidate_indices], matrix[fitted.vacancy_index]
).ravel() * 100
# Если строка кандидата имеет nnz == 0, вместо числа возвращается None.
```

Старые версии результатов не пересчитываются. `weighted_ranking.py`, старые
функции покрытия и графового рейтинга оставлены для исторической совместимости
и их тестов; активные HTTP-расчёты их для ранжирования не вызывают.
Neo4j хранит зеркало нового рейтинга, не вычисляет для него иной Score.

## Оценка качества и ограничения

`tools/evaluate_scoring.py` оценивает этот же cosine-рейтинг. `--calibrate`
подбирает только порог бинарного решения на validation: он не меняет рейтинг.
В отчёте отдельно указаны неоценённые пары; классификация и ROC-AUC считаются
только по оценённым, ранжирование учитывает неоценённых в конце списка.
Вместе с метриками необходимо сообщать число отказов от оценки.

Score — лексическая близость, не вероятность пригодности и не доля выполненных
требований. Нет автоматического понимания всех синонимов, перевода языков,
уровня владения и давности опыта. Ошибки парсера, повторение ключевых слов и
посторонний текст влияют на результат. Качество требует размеченных примеров.

Проверки: `python -m unittest discover -s tests -p "test_cosine_ranking.py" -v`.
Они независимо воспроизводят математику, проверяют один fit, точность сортировки,
нулевой/отсутствующий балл, HTTP 422 и одинаковый рейтинг обоих маршрутов.
