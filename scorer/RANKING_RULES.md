# Порядок кандидатов

Контракт `coverage-tfidf-id-v1`: покрытие обязательных навыков по убыванию,
затем TF-IDF по убыванию, затем стабильный ID. Отсутствующая оценка TF-IDF
идёт после нулевой при одинаковом покрытии. Покрытие без обязательных навыков
остаётся нулевым, как в существующем `analyze_skills`.

Это правило сохраняет приоритет покрытия, но не является сортировкой по одному
TF-IDF. Для бенчмарка эти два порядка нужно оценивать отдельно. Числа TF-IDF
не являются вероятностью пригодности кандидата.

`build_candidate_metrics` проверяет соответствие числа оценок и кандидатов,
уникальность ID и допустимость чисел. Он передаёт графу только идентификаторы,
обезличенные подписи и текстовое сходство. Покрытие вычисляет Neo4j по снимку
навыков прогона; тот же порядок реализован в `ranking_key` для проверок.

`RESULT_FIELDS` задаёт публичные поля результатов. Исторические записи можно
проецировать через `public_result`, сохраняя исходный порядок и помечая записи
без версии как `legacy`. Это не пересчёт старой истории новым правилом.

Последовательность компонентных PR: сначала добавить этот контракт в Scorer,
затем переключить Backend на него и обновить Testing, после чего убрать старые
модули вычисления из Scorer. Frontend и Core получают отдельные изменения.
Проверочная копия объединяет эти изменения только как файлы для тестирования;
Git-ветки от этого не объединяются.
