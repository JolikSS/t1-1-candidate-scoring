# Контракт профессиональных выражений

Правила `expressions-1.0` используют только стандартную библиотеку Python.
Словарь вариантов и глаголов находится в `expression_catalog.py`, поиск — в
`professional_expressions.py`. Обёртка `skill_matching.py` сохраняет старый интерфейс.

## Результат извлечения

`extract_professional_expressions(text, catalog, section=...)` возвращает
`ExpressionMention` для каждого распознанного упоминания:

- `canonical`: стабильное имя (`node.js`, `develop:rest api`);
- `name`: отображаемое имя; `kind`: `skill` или `activity`;
- `text`, `start`, `end`: точный фрагмент и позиции в исходной строке Python;
- `section`: раздел, явно переданный вызывающим кодом;
- `negated`, `negation_kind`, `cue`: отрицание, его тип и формулировка.

Поиск выполняется по исходному тексту с игнорированием регистра. Текст целиком
не переводится через `casefold`, поэтому Unicode-преобразования не сдвигают позиции.
При пересечении совпадений с одинаковым началом выбирается более длинное.
Например, в каталоге с VMware и VMware ESXi явное `VMware ESXi` даёт составной
термин. Отдельно упомянутый VMware сохраняется. Иерархии навыков не выводятся.

## Варианты и действия

Сохраняются существующие варианты, добавлены .NET, CI/CD, CSharp и другие явные
написания. Пробелы внутри технической пунктуации допускаются. Известные составные
названия защищают границы даже при узком каталоге: запрос одного JavaScript не
находит JS внутри `Node . JS`. .NET не выводится из подстроки ASP.NET.
Python 2/3 с перечисленным форматом числовой версии приводится к Python;
исходная версия остаётся в свидетельстве `text`.

Правила действий связывают указанные варианты глаголов с ближайшей известной
технологией: разработка, администрирование, настройка, развёртывание, тестирование.
Между глаголом и технологией допускается один предусмотренный предлог. Например,
`разработка REST API`, `разрабатывал RESTful API`, `developed REST API` дают
`activity:develop:rest api`. Само упоминание API не означает REST API.
Произвольные промежуточные слова и семантические эквиваленты не угадываются.
Совпадение фиксирует формулировку, а не подтверждает уровень владения технологией.

## Отрицания и старый интерфейс

Различаются отрицательный опыт (`experience`) и отрицание требования (`requirement`).
Область формулировки ограничена предложением, строкой, точкой с запятой и
противопоставлением. Списки могут наследовать отрицание; явная положительная
формулировка сбрасывает его. Точка внутри Node.js не является границей предложения.

`find_skill_mentions` сохраняет имена и порядок переданного каталога, удаляет
повторы по каноническому имени и исключает отрицательный опыт. Как и раньше,
отрицание обязательности остаётся видимым вызывающему классификатору вакансии:
он должен сформировать `not_required`. Это нужно для совместимости с Parser.
Для новой подготовки признаков нужно использовать структурированный результат,
а не считать любой элемент старого списка положительным требованием.

## Подготовка TF-IDF

`normalize_professional_text` заменяет только распознанные названия их
каноническими формами. Неизвестные слова, прочая пунктуация и отрицания сохраняются.
Повторная нормализация должна давать тот же текст.

`professional_features` выдаёт целые ключи `skill:node.js`, `skill:.net`,
`activity:develop:rest api`. Отрицательные упоминания не дают положительный ключ.
При `include_negated=True` они получают отдельный префикс `negated:`.
Частоты реальных повторных упоминаний сохраняются.

Ключи подключены через callable-анализатор `tfidf_features.py`; детали корпуса,
остаточных слов, частотных усилений и ограничений описаны в `TFIDF_RULES.md`.
Одной нормализации строки недостаточно для правильного учёта отрицаний в TF-IDF.

## Проверки и оставшиеся ограничения

`python -m unittest discover -s tests -p "test_professional_expressions.py" -v`
не требует БД, sklearn или модели. Совместимость с Parser 8eee41d проверяется
отдельно на изолированной копии его файлов, без merge компонентных веток.
Локальный отчёт на архивах сохраняет только хеши, имена навыков и счётчики.

Словари конечны. Сложные отрицания, местоимения, разорванные PDF-колонки и
несколько несвязанных утверждений без разделителей могут потребовать ручной
проверки. Изменение числа совпадений не является измерением точности.
Существующая группа SQL включает унаследованные варианты Microsoft SQL;
разделение языка SQL и отдельных СУБД — отдельное решение об устройстве справочника.
Пересчёт MongoDB, сохранение новых свидетельств, формула TF-IDF, E5 и сортировка
в этом блоке не изменяются. Бенчмарк ранжирования остаётся отдельной работой.
