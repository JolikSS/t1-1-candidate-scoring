# Подбор кандидатов по профессиональным выражениям и TF-IDF

Проект извлекает профессиональные разделы вакансий и резюме, нормализует выражения
по словарю и регулярным выражениям и сравнивает их через корпусный TF-IDF.
MongoDB хранит документы, снимки входных данных, историю расчётов и решения HR.
Neo4j подключается дополнительно. Полное описание бэкенда, схемы хранения,
REST API и примеры запросов: [docs/BACKEND.md](docs/BACKEND.md).
Результаты технических проверок: [docs/VERIFICATION.md](docs/VERIFICATION.md).
Оценка качества, подбор весов, проверка реального графа и мониторинг:
[docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).

## Запуск только бэкенда

Python 3.10+, зависимости из requirements.txt, настройки из .env.example:

```bash
docker compose up -d mongo
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

Документация API: http://127.0.0.1:8000/docs.
Новый API: независимая загрузка резюме, редактирование вакансий и критических
навыков, POST /scoring-runs с итоговым Score, история и снимки входов,
POST /feedback с бинарной оценкой HR и экспорт разметки.
GET /resumes/{id}/text возвращает подготовленный текст; source=true — исходный.
Бэкенд рассчитан на локальный запуск без пользовательской авторизации.

## Запуск в Windows

1. Выберите Python 3.10+ и создайте .venv. Установите requirements.txt;
   для проверок дополнительно requirements-dev.txt.
2. Скопируйте .env.example в .env и настройте MongoDB. Для дополнительного Neo4j
   задайте NEO4J_ENABLED=true и пароль. Docker Compose поддерживает обе базы;
   для нативного запуска предусмотрены пути в .env.example.
3. Пользовательские vacancies.zip и resumes.zip положите в data/ или задайте
   CANDIDATE_DATA_DIR. Оба архива остаются локальными вне Git.
4. Запустите `.\.venv\Scripts\python.exe run_project.py` из корня проекта.
   Интерфейс доступен на http://127.0.0.1:8501; остановка — stop_project.py.

Выбранного окружения приложения достаточно для расчёта: отдельные модели
и процессы кодирования текстов не используются.

## Данные и результаты

Вакансию можно выбрать из MongoDB или загрузить ZIP. Архив резюме необязателен,
если документы уже сохранены. SHA-256 предотвращает повторное создание одного
резюме при одинаковых исходных байтах. Изменение парсера само не переразбирает
сохранённые документы: обновление данных требует отдельного контролируемого шага.

TF-IDF получает заново прочитанные активные записи корпуса. Новые готовые
выражения не разбиваются на части; отрицания известных технологий учитываются
до формирования положительных признаков. Неизвестные слова сохраняются.
Подробности: scorer/TFIDF_RULES.md и scorer/PROFESSIONAL_EXPRESSIONS.md.

Активный алгоритм `corpus-tfidf-cosine-v3`: итоговый Score равен
`100 × cosine(TF-IDF резюме, TF-IDF вакансии)`. Оба API и Streamlit используют
единый рейтинг без смеси 70/30, приоритета покрытия и множителей критических навыков.
Сортировка выполняется по полной точности, затем по ID. Округляется только отображение.
Резюме без признаков получает `score=null`, `status=insufficient_text`; вакансия
без признаков отклоняется с HTTP 422. Нулевое измеренное сходство остаётся числом 0.
Формула, состав корпуса, подготовка признаков и независимое воспроизведение:
[scorer/COSINE_RANKING.md](scorer/COSINE_RANKING.md).

Профиль нового расчёта по умолчанию — `lemmas-ru-en-v2`; в `/scoring-runs` можно
явно выбрать `expressions-v1`. Старые записи остаются со своими версиями.
Параметры coverage_weight/critical_multiplier больше не принимаются.

При включении Neo4j материализует требования и снимки навыков в рамках прогона. Старые
снимки сохраняются. История MongoDB возвращается в сохранённом порядке через
публичный набор полей; записи без версии помечаются legacy. Старые графовые
прогоны с другой версией требуют нового расчёта. Старые данные и локальные
артефакты не удаляются автоматически.

При ошибке расчёта или MongoDB API возвращает ошибку. Резюме, сохранённые до
ошибки, доступны для повтора. В новом API Neo4j служит дополнительным зеркалом,
его сбой не отменяет результат MongoDB. Старый /score при использовании графа
сохраняет прежний контракт ошибок. Общей транзакции между хранилищами нет.

## Проверки

python -m unittest discover -s tests -v

Общий запуск тестов и стиля: `python tools/check_backend.py`.
В GitHub Actions предусмотрены проверки Python 3.10/3.12 и настоящих MongoDB/Neo4j.

Изолированная проверка настоящего HTTP API и MongoDB:
`python tools/verify_backend.py`. Она использует собственную временную БД,
проверяет пакет из 100 PDF/TXT, конкурентные загрузки, снимки и обратную связь HR,
после чего удаляет только свои тестовые данные.

Проверка настоящих сервисов: python tools/verify_pipeline.py. Она загружает
настроенные локальные архивы, проверяет повторные загрузки, историю и совпадение
HTTP-результатов с графом. Её успешность нельзя заявлять по тестам с двойниками БД.

Оценка релевантности выполняется отдельным бенчмарком на согласованной разметке.
Изменение оценок или порядка кандидатов само по себе не доказывает рост качества.

Лимиты: 500 PDF/TXT, 20 МиБ на документ, 512 МиБ на пакет, 2 МиБ извлечённого текста. Сканы без текста
требуют OCR, которого здесь нет. Очистка личных данных остаётся эвристической.
Исходные документы, .env и локальные отчёты не включаются в Git.

## Компоненты и API

Parser — структура документов и должности; Scorer — выражения, TF-IDF и правило
сортировки; Backend — API, MongoDB и Neo4j; Frontend — Streamlit; Core — запуск,
настройки и зависимости; Testing — интеграционные проверки.
feature/benchmark сохраняет самостоятельный рабочий процесс участника команды.

API v4 описан в docs/BACKEND.md и /docs. Совместимые маршруты API v3:
GET /health, /vacancies, /resumes; POST /vacancies/upload, /score;
GET /vacancies/{id}/results. Схема — /docs. Ответ /score содержит ranking_version.
Поля нового результата перечислены в scorer/cosine_ranking.py, COSINE_RESULT_FIELDS.
