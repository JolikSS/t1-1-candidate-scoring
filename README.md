# Рабочий гибридный пайплайн

## Запуск

1. Установите Python 3.10+ и зависимости `requirements.txt`. Для тестов добавьте `requirements-dev.txt`.
2. Создайте `.env` по `.env.example`. Настройте MongoDB и Neo4j; Docker Compose запускает обе БД. Для нативного Windows-запуска задайте пути MongoDB, Neo4j и Java 21.
3. E5 работает в отдельном процессе. Установите `requirements-embeddings.txt` в отдельное окружение и задайте `EMBEDDING_PYTHON`. Модель — `intfloat/multilingual-e5-base`, revision `d128750597153bb5987e10b1c3493a34e5a4502a`. `E5_MODEL_PATH` позволяет использовать уже загруженный снимок.
4. Положите пользовательские `vacancies.zip` и `resumes.zip` в `data/` либо укажите `CANDIDATE_DATA_DIR`. Если база уже заполнена, повторная загрузка резюме не нужна.
5. Запустите `run_project.py` кнопкой Run в PyCharm. Откроется UI на http://127.0.0.1:8501. Остановка — `stop_project.py`; данные обеих баз сохраняются.

## Данные и расчёт

UI сохраняет два поля загрузки ZIP и таблицу. Вакансию можно выбрать из MongoDB без ZIP; новый архив вакансий сохраняется целиком. Архив резюме необязателен: новые документы добавляются к сохранённому корпусу. SHA-256 исходных байтов проверяется до парсинга; повторная загрузка сохраняет ID и не создаёт нового кандидата. Изменённый файл считается новым документом.

TF-IDF и E5 получают только заново прочитанные записи MongoDB. Скрытые и пустые записи исключаются. TF-IDF обучается на общем активном корпусе без повторного добавления текущих документов. E5 использует `query:` и `passage:`, фрагменты до 448 токенов с перекрытием 64 и нормализованные векторы. Метрика E5 — среднее лучших совпадений для фрагментов вакансии. Кеш зависит от текста, префикса, revision и версии подготовки; при повреждении пересчитывается. Первый полный расчёт значительно дольше повторного, запрос допускает до 30 минут.

RRF объединяет позиции в рейтингах TF-IDF и E5: `1/(60+rank_tfidf) + 1/(60+rank_e5)`. Сортировка: покрытие обязательных навыков ↓, RRF ↓, стабильный ID. Покрытие не заменяется семантикой: E5 может ошибаться на отрицаниях.

Neo4j хранит вакансии, резюме, навыки, прогоны и снимки навыков. Запрос проходит от прогона к требованиям и к навыкам снимка резюме, вычисляет найденные/недостающие навыки и сортирует результаты. В MongoDB сохраняется история вместе с ID графового прогона. Снимки изолируют старые прогоны от последующих изменений. При сбое E5 или Neo4j API возвращает ошибку, а не незаметно переключается на другой рейтинг; загруженные резюме остаются в MongoDB для повтора. Базы не объединены общей транзакцией: после ошибки записи истории завершённый графовый прогон может остаться без записи в MongoDB.

## Проверки

`python -m unittest discover -s tests -v`

Полная проверка настоящих сервисов и архивов: `python tools/verify_pipeline.py`. Она добавляет реальные документы через API, дважды рассчитывает корпус, проверяет дедупликацию, кеш, графовый порядок и историю. Отчёт содержит только агрегаты.

Лимиты: 500 PDF/TXT на пакет, 20 МБ на документ, 512 МБ на архив/распакованный пакет. ZIP обрабатывается в памяти. Сканы без текстового слоя требуют OCR, которого здесь нет. Очистка личных сведений остаётся эвристической. Документы, векторы, модели, `.env` и логи должны оставаться локальными вне Git.


## Основные файлы

- `Parser/resume_parser.py`, `vacancy_parser.py` — правила извлечения и очистки.
- `db/mongo_store.py` — документы, хеши, история.
- `scorer/text_similarity.py`, `semantic_similarity.py`, `fusion.py` — TF-IDF, отдельный процесс E5, RRF.
- `db/graph_store.py` — графовые снимки навыков и запрос ранжирования.
- `api/main.py`, `ui/app.py` — HTTP API и простой интерфейс.
- `tools/local_runtime.py` — запуск/остановка только принадлежащих этому клону процессов.
- `tools/bootstrap_data.py`, `verify_pipeline.py` — предзагрузка и сквозная проверка.

API: `GET /health`, `/vacancies`, `/resumes`; `POST /vacancies/upload`, `/score`; `GET /vacancies/{id}/results`; схема запросов — `/docs`. `/score` без файлов использует сохранённый активный корпус. `uploaded_only=true` оставлен для совместимости API и ограничивает кандидатов файлами текущей загрузки; UI использует весь корпус.

Для существующей базы ZIP при запуске необязательны. Повторное извлечение изменённой версией парсера намеренно не выполняется автоматически: дедупликация сохраняет прежний разбор. Справочник навыков актуализируется по уже сохранённому очищенному тексту при расчёте, без исходных PDF.

## Назначение веток

Готовая объединённая версия находится в `main`. Рабочие изменения распределяются по существующим веткам:

| Ветка | Компонент |
|---|---|
| `Frontend` | Streamlit UI и лимит загрузки ZIP |
| `Backend` | API, MongoDB и граф Neo4j |
| `Parser` | Профессиональные разделы резюме и подтверждения навыков |
| `Scorer` | Корпусный TF-IDF, локальная E5 и RRF |
| `Testing` | Автотесты и сквозная проверка реальных сервисов |
| `Core` | Запуск/остановка, окружение, зависимости и Docker Compose |
| `feature/benchmark` | Предзагрузка локальных архивов и дедупликация |

В PyCharm сначала выберите Python-интерпретатор подготовленного окружения в настройках проекта, затем запускайте `run_project.py`. Лаунчер проверяет основные зависимости, отдельное окружение E5 и локальный путь модели. Параллельный запуск и остановка синхронизированы; повторный Run не останавливает уже работающий экземпляр.

Проверка после запуска из PyCharm: расчёт 195 резюме вернул HTTP 200, 1140 попаданий в кеш E5 и 0 новых кодирований; время — 58,33 с на проверенном компьютере. Терминальные управляющие коды в выводе процесса E5 не мешают чтению JSON.
