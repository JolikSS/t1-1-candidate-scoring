## Что передаётся в Git

- `catalog.json`: SHA-256 всех 55 вакансий и 196 резюме, укрупнённые роли, хеши архивов и seed.
- `selection.json`: зафиксированные 50 пар, разделение и происхождение каждого документа по хешу.
- `ANNOTATION_GUIDE.md`: бинарная релевантность, неопределённость, обязательные доказательства.
- `examples.synthetic.csv`: вымышленные обезличенные примеры применения инструкции; это не реальные метки.
- `../../tools/benchmark_data.py`: воспроизведение отбора, локальные формы, сверка, согласование и заморозка.
- `../../tests/test_benchmark_data.py`: проверки целостности и защиты от неполной разметки.

Реальные PDF, исходные имена файлов, контакты, тексты, комментарии разметчиков и финальные метки
хранятся только в `data/evaluation/`, уже исключённой из Git. Не применять `git add -f` к этой папке.
Хеши служат контролю происхождения и целостности, а не основанием считать реальные документы публичными.

## Происхождение и отбор

Источник — переданные командой архивы вакансий и резюме. Правовой статус/согласие на публикацию
не установлены; документы не публикуются. Побайтовые хеши архивов записаны в `catalog.json`.
Все 251 PDF локально прочитаны через pypdf; ошибок чтения не обнаружено.
Это техническая проверка наличия текста, а не подтверждение качества парсера приложения.

Каталог ролей подготовлен по заголовкам должностей из документов с исправлением явных ошибок
извлечения заголовка. Использованы текущий парсер заголовков и ручной просмотр списка;
оценки, признаки TF-IDF и ответы скорера для отбора не рассчитывались.
Роль — укрупнённый признак стратификации, не метка соответствия вакансии.
`devops` включает системное администрирование; `backend` включает разные серверные технологии.
Прочие роли сохранены в каталоге как `other`, но не участвуют в выборе пяти вакансий.

Алгоритм отбора `pilot-selection-v1`:

1. Из каждой группы `backend`, `cpp`, `data-science`, `devops`, `frontend` выбирается одна вакансия.
   Порядок определяется лексикографически по SHA-256 строки `seed|vacancy|document_sha256`.
2. Пять вакансий сортируются по SHA-256 `seed|split|document_sha256`:
   первые две — `validation` (разработка), остальные три — `test` (финальная проверка).
3. Для каждой вакансии выделяется 6 резюме той же группы, затем 2 смежной группы, затем 2 из
   всех оставшихся. Сначала резервируются профильные резюме **для всех вакансий**, затем смежные,
   затем случайный фон. Внутри этапа вакансии идут в порядке шага 2.
4. Резюме сортируются по SHA-256 `seed|vacancy_sha256|stratum|resume_sha256`.
   Уже выбранные резюме исключаются глобально. Смежность зафиксирована в `ADJACENT` скрипта.
   Фоновый кандидат может оказаться подходящим; профильный — неподходящим.
5. ID — `v-`/`r-` и первые 16 символов SHA-256. Полные хеши сохранены; коллизии проверяются.

Seed: `pilot-50-v1-2026-11-11`. Повторный отбор по неизменному каталогу даёт тот же манифест.
Представительность ограничена: IT-роли, один источник, квоты 6/2/2, малая C++-группа (взяты все 6).
Это не случайная выборка рынка и не гарантия наличия положительных меток у каждой вакансии.
Нельзя заменять неудобные пары после просмотра меток или результатов алгоритма.
Побайтовые повторы исключены; совпадение личности или почти одинаковые редакции резюме этим не гарантируются.
Если при ручном просмотре обнаружены такие повторы между частями, остановить пилот и выпустить новую
версию отбора до оценки, записав причину; не исправлять текущую версию незаметно.

| Часть | Вакансий | Пар | Использование |
|---|---:|---:|---|
| validation | 2 | 20 | Разработка и разбор ошибок |
| test | 3 | 30 | Единственная финальная оценка после заморозки алгоритма |

Совпадений полных SHA-256 между частями нет. Манифест фиксируется коммитом до разметки.
Контрольные суммы выявляют изменения, но не заменяют права доступа или внешнюю фиксацию коммита.

## Команды

Из корня репозитория, Python 3.10+. Инструмент использует только стандартную библиотеку,
не требует MongoDB, sklearn или запуска API.

```powershell
python tools/benchmark_data.py validate
python -m unittest tests.test_benchmark_data -v
python tools/benchmark_data.py prepare --vacancies "C:/path/vacancies (1).zip" --resumes "C:/path/resumes (1).zip"
```

`prepare` проверяет архивы по хешам и создаёт `data/evaluation/pilot-v1/`:

- 55 PDF с непрозрачными ID в `documents/validation/` и `documents/test/`;
- `source_map.private.json` — связь ID, исходного имени, хеша и локального пути;
- `selection.lock.json` — копию проверенного манифеста;
- `annotator_a.csv`, `annotator_b.csv` — по 50 пустых строк с разным порядком;
- `PAIR_INDEX.md` — как найти документы по `pair_id`.

ID пары состоит из ID вакансии и ID резюме через `__`. Разметчик открывает два соответствующих PDF.
PDF содержат исходные персональные сведения: работать локально, учитывать только профессиональное
содержание; не переносить контакты/имена в доказательства и не пересылать документы публично.
Каждый участник получает свою форму и доступ к документам, без чужой формы и результатов скорера.

Скрипт не перезаписывает существующие файлы. Для повторной технической подготовки используйте отдельный
`--output data/evaluation/pilot-v1-copy`; не удаляйте заполненные формы.
Для проверки детерминизма без замены манифеста:

```powershell
python tools/benchmark_data.py --manifest data/evaluation/reselected.json select
```

После **реальной независимой** разметки обоими участниками:

```powershell
python tools/benchmark_data.py reconcile --a data/evaluation/pilot-v1/annotator_a.csv --b data/evaluation/pilot-v1/annotator_b.csv --output data/evaluation/pilot-v1/reconciliation
```

Будут созданы `agreement.json`, журнал `disagreements.csv` и незаполненный `adjudication.csv`.
Журнал содержит все разные метки и все случаи `U`, включая `U/U`.
Доля совпадений — простое согласие до обсуждения; это не экспертная точность и не оценка модели.
После совместного обсуждения заполните `final_label` (0/1), `resolution` и `adjudicators` в каждой строке.
Нельзя молча заменять исходные ответы разметчиков.

```powershell
python tools/benchmark_data.py finalize --a data/evaluation/pilot-v1/annotator_a.csv --b data/evaluation/pilot-v1/annotator_b.csv --adjudication data/evaluation/pilot-v1/reconciliation/adjudication.csv --output data/evaluation/pilot-v1/frozen --attest-independent
```

`--attest-independent` подтверждает, что два разных человека работали независимо и без оценок алгоритма.
Скрипт проверяет разные reviewer_id и полноту, но технически доказать независимость людей не может.
Итог: `judgments.json` (50 согласованных меток), `test.frozen.json` (30 финальных меток), `freeze.json`
с хешами выбора, ответов, согласования и итоговых файлов; исходные формы копируются рядом для аудита.
Файлы создаются без возможности перезаписи через инструмент. Хеш `test_sha256` из `freeze.json`
нужно отдельно зафиксировать коммитом/у ответственного №8 до финального прогона.

## Передача участнику №8

Формат `pilot-judgments-v1` — контракт разметки, а не готовый вход старого `evaluate_scoring.py`.
В `judgments` находятся `vacancy_id`, `resume_id`, `split` (`validation`/`test`), `label` (целое 0/1).
Документы связываются по ID через локальную карту. ID бенчмарка не заменяют ID документов API:
для интеграции сопоставлять SHA-256 и сохранять явную таблицу соответствия.
Доказательства и журнал разногласий остаются локально.

№8 адаптирует загрузку к единому парсеру/TF-IDF, фиксирует состав корпуса и версии, рассчитывает
precision@5, nDCG@5 и MAP. Этот пакет не меняет скорер, API, парсеры или чужой инструмент оценки.
Нельзя запускать старую смешанную формулу и называть её чистым TF-IDF.
Без согласованных меток метрики качества не публикуются. По каждой вакансии нужно показать число
положительных примеров, включая ноль; не заменять вакансии, чтобы улучшить метрики.

Разработчики не должны получать test-метки до заморозки алгоритма. Два разметчика неизбежно их видят:
организационное ограничение доступа обеспечивает ответственный №8, сам Git или скрипт этого не делает.
После просмотра финальных результатов и изменения алгоритма test становится открытой частью;
для независимой проверки нужен новый набор и новая версия.
