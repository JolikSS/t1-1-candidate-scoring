## Зависимости и Neo4j

Во всех четырёх requirements-файлах прямые зависимости зафиксированы через `==`.
Полные транзитивные версии: `requirements-lock-linux-py312.txt` и
`requirements-lock-windows-py313.txt` (Windows дополнительно с хешами пакетов).
В `.vscode/settings.json` указан локальный интерпретатор `.venv`.

Импорт драйвера перенесён в создание `GraphStore`: выключенная Neo4j больше не
мешает импортировать backend без драйвера. При отсутствующем драйвере выводится
понятная ошибка о выбранном Python, установке requirements и затенении `neo4j.py`.
`tools/check_environment.py` показывает расхождения версий и путь драйвера.
Проверены настоящее соединение с Neo4j Community 5.26.0, драйвер 5.28.8,
ограничения, ранжирование, чтение, снимки истории и запись weighted-результатов.
Отчёт: `reports/neo4j_integration.json`. Полный запуск MongoDB + Neo4j здесь не выполнялся.

## Каталог и извлечение

Расширен общий каталог hard/soft skills: основы программирования, тестирование,
web/security, данные и аналитика, администрирование, сети, коммуникация и другие
явные компетенции. Названия и варианты: `scorer/skill_catalog_extension.py`.

Обычный режим — regex. Опциональный spaCy использует PhraseMatcher и Matcher
с тем же каталогом, без скачивания языковой модели. Есть выбор обоих движков
для вакансий и резюме. Русские формы и составные технические названия проверяются
отдельно; Unicode-дефисы не должны ломать совпадения.
Готовая русская модель не является готовым распознавателем навыков.
Обучаемый NER не обучался: на доступных данных расширение словаря уже дало
recall выше 0.6; для обучения понадобятся независимые примеры с границами сущностей.

«Обучим Python», отрицания, желания, обязанности и стек сохраняют свои роли.
Контекст не становится обязательным требованием. Профессиональные выражения
поступают в существующий TF-IDF через канонические `skill:...` признаки;
формула рабочего ранжирования не заменена.
Старые сохранённые документы нужно разобрать/пересчитать заново.

## Загрузка JSON и метрики

`check_skills.py` — локальная страница без баз данных. В основном UI есть такой
же раздел «Проверка навыков». Загружаются JSON/ZIP эталонов и PDF/TXT/ZIP документов.
Отображаются micro recall/precision, recall каждого документа, лишние навыки,
пропущенные группы и ошибки ролей. Отчёт скачивается как JSON.
Изменение файлов, разметки или движка сбрасывает предыдущий результат.

Поддержаны простой массив навыков, объект резюме с `skills` и ваши объекты
вакансий с `required_skills`, `preferred_skills`, `additional_skills_from_tasks`,
`additional_skills_from_skill_list`, `stack`. Стаж и образование не включаются
в число навыков. Ошибки чтения не пропускаются молча.

Полные эталонные предложения нельзя прогонять через проверяемый парсер, чтобы
получить его же «правильные ответы». Для 101 предложения пяти предоставленных
вакансий подготовлена отдельная ручная декомпозиция:
`tests/fixtures/provided_reference_annotations.json`. Это начальная разметка
разработки, а не независимый эталон второго участника. В ней оставлены неизвестные
каталогу понятия, поэтому пропуски действительно входят в знаменатель recall.
Ожидаемые понятия видны и редактируются в таблице перед расчётом.

`A; B` означает две компетенции; `A | B` — одну группу допустимых альтернатив.
Одно найденное понятие не может закрыть две разные группы. Precision групп =
закрытые группы / (закрытые группы + навыки вне эталона); recall = закрытые группы /
все группы. Дополнительные члены одной альтернативной группы не штрафуются.
При пустом знаменателе значение — null, а не фиктивная единица.
Эталон должен быть полным: неразмеченные реальные упоминания попадут в лишние.

CLI для исходных загруженных форматов:

```powershell
.\.venv\Scripts\python.exe -m tools.evaluate_uploaded_skills "Требования JSON.zip" new_resume.zip -o reports/my_recall.json
```

Движок меняется через `--backend spacy`. Для простого массива навыков резюме
нужен `--array-kind resume`. Каталог не строится автоматически из эталонных ответов.

## Результат на предоставленных данных

Точные результаты: `reports/remarks_summary.json` и
`reports/provided_vacancies_regex.json`, `reports/provided_vacancies_spacy.json`.
Каталог 1.5 в сравнении запускается с текущими общими правилами; это сравнение
каталогов, а не заявление о запуске старого исторического кода.

Все пять vacancy.pdf побайтно совпадают с прежним набором 55 вакансий:
`reports/provided_corpus_overlap.json`. Они являются данными разработки.
Превышение 0.6 на них не подтверждает recall на новых независимых вакансиях.
Резюме из архива прочитаны, но без эталона навыков их recall не заявляется.

Для контрольного запуска остался строгий формат `schema_version: 1`,
`split: holdout`, `annotation_status: reviewed`, массив cases с text/source_file
и gold по ролям required/preferred/responsibilities/context/conditions/not_required.
Навыки — канонические понятия либо объекты `any_of`.

```powershell
.\.venv\Scripts\python.exe -m tools.evaluate_skill_extraction holdout.json --development development.json -o reports/holdout.json
```

Контрольные тексты сверяются с development и прежними 55 документами по хешам;
перефразированные дубликаты должен проверить участник команды. Настройка по
ошибкам контрольной выборки превращает её в development. До нового независимого
набора цель recall >= 0.6 на holdout остаётся неподтверждённой.

## Калибровка coverage и critical multiplier

`coverage_weight=0.7` задаёт долю покрытия навыков в итоговом балле.
`critical_multiplier=2.0` задаёт вес критического обязательного навыка.
Это разные параметры; они не являются recall парсера.

Пользователь подтвердил, что разметки пригодности резюме пока нет. Поэтому
значения рабочего скорера не подбирались по выдуманным меткам и не менялись.
Подготовлен `docs/examples/pair_labels.csv` с 50 реальными ID пар и пустыми полями.
Нужно заполнить label=0/1, domain и split=train/validation/test. Для одной вакансии
и одного резюме split должен быть одинаковым во всех строках: нельзя подмешивать
одни и те же документы в validation и test. В каждой из этих частей нужны
положительные и отрицательные примеры. Отдельно укажите critical_skills через `;`,
одинаково для всех строк одной вакансии и только из её required_skills.
Если критические навыки не отмечены, множитель 2.0 сохраняется и не объявляется
откалиброванным: этот параметр на таких данных не влияет на оценку.

После заполнения CSV:

```powershell
.\.venv\Scripts\python.exe -m tools.build_ranking_dataset new_resume.zip docs/examples/pair_labels.csv --source real -o data/evaluation/ranking.json
.\.venv\Scripts\python.exe -m tools.evaluate_scoring data/evaluation/ranking.json --calibrate --extraction-report reports/holdout.json --output reports/calibration.json
```

Для real-калибровки обязателен контрольный отчёт recall по текущему коду и каталогу
с recall >= 0.6 и precision не ниже сравниваемого базового варианта.
`scorer/calibration_gate.py` блокирует development-отчёты и устаревший код.
Параметры выбираются по validation; test используется только для финальной оценки.
Синтетическая проверка этого механизма — `reports/calibration_smoke.json`;
её параметры не являются рекомендацией для рабочего скорера.

## Что нельзя считать завершённым без новых данных

- Подтверждение recall >= 0.6 на независимом наборе вакансий/резюме.
- Реальная калибровка скорера без меток пригодности и критических навыков.

Код загрузки, метрик, проверок независимости и калибровки подготовлен, но
эти два результата нельзя заменить высоким числом на development или синтетике.
