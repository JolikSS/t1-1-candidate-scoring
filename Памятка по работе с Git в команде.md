## Основной рабочий цикл

|Действие|Терминал|Расширение / интерфейс редактора|
|---|---|---|
|Перейти в основную ветку|`git switch main`|Переключить ветку через индикатор ветки|
|Получить изменения|`git pull --ff-only`|**Pull**|
|Создать рабочую ветку|`git switch -c feature/task-name`|**Create New Branch**|
|Посмотреть изменения|`git status` и `git diff`|Панель **Source Control**|
|Подготовить файлы|`git add <файл>`|Нажать `+` возле нужных файлов|
|Создать коммит|`git commit -m "feat: add search"`|Ввести сообщение → **Commit**|
|Отправить ветку|`git push -u origin feature/task-name`|**Publish Branch** / **Push**|
|Создать Pull Request|Через GitHub/GitLab CLI или сайт|**Create Pull Request**|
|Обновить ветку перед слиянием|`git fetch origin` → `git rebase origin/main`|**Fetch** → **Rebase Branch**|
|Удалить локальную ветку после слияния|`git switch main` → `git branch -d feature/task-name`|**Delete Branch**|

## Перед началом задачи

```
git switch main
git pull --ff-only
git switch -c feature/task-name
```

Не работайте непосредственно в `main` или `master`. Для каждой задачи создавайте отдельную ветку.

Примеры названий:

```
feature/user-search
fix/login-redirect
refactor/payment-service
docs/api-guide
```

## Сохранение изменений

Сначала проверьте, что изменилось:

```
git status
git diff
```

Добавляйте только относящиеся к задаче файлы:

```
git add src/search.ts
git commit -m "feat: add user search"
```

В редакторе откройте **Source Control**, просмотрите изменения, добавьте нужные файлы в **Staged Changes** и создайте коммит.

Не используйте `git add .` вслепую: в коммит могут попасть временные файлы, секреты или чужие изменения.

## Сообщения коммитов

Рекомендуемый формат:

```
тип: краткое описание
```

Основные типы:

- `feat` — новая возможность;
    
- `fix` — исправление ошибки;
    
- `refactor` — изменение кода без изменения поведения;
    
- `docs` — документация;
    
- `test` — тесты;
    
- `chore` — обслуживание проекта;
    
- `style` — форматирование.
    

Примеры:

```
feat: add profile filters
fix: prevent duplicate form submission
docs: update local setup guide
```

Один коммит — одно логически завершённое изменение.

## Отправка ветки и Pull Request

```
git push -u origin feature/task-name
```

После первой отправки достаточно:

```
git push
```

В Pull Request укажите:

- что изменено;
    
- зачем это сделано;
    
- как проверить;
    
- связанные задачи;
    
- скриншоты для изменений интерфейса.
    

Не объединяйте Pull Request без успешных проверок и необходимого ревью.

## Обновление рабочей ветки

Перед Pull Request или слиянием получите актуальное состояние основной ветки:

```
git fetch origin
git rebase origin/main
```

Если ветка уже опубликована и после `rebase` изменилась история:

```
git push --force-with-lease
```

Используйте только `--force-with-lease`, а не обычный `--force`. Не переписывайте историю ветки, над которой работают другие люди, без согласования.

Если команда использует merge вместо rebase:

```
git fetch origin
git merge origin/main
```

Следуйте одному принятому в команде подходу.

## Разрешение конфликтов

Во время `rebase` или `merge` Git отметит конфликтующие файлы.

1. Откройте конфликт в редакторе.
    
2. Выберите или объедините нужные изменения.
    
3. Удалите маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
    
4. Запустите тесты.
    
5. Отметьте конфликт решённым.
    

При `rebase`:

```
git add <исправленные-файлы>
git rebase --continue
```

Отменить процесс:

```
git rebase --abort
```

При `merge`:

```
git add <исправленные-файлы>
git commit
```

Отменить процесс:

```
git merge --abort
```

В редакторе используйте встроенный **Merge Editor**, затем добавьте исправленные файлы в staged changes и продолжите операцию.

## Временное сохранение незавершённой работы

```
git stash push -m "WIP: profile form"
git stash list
git stash pop
```

В редакторе: **Source Control → Stash Changes**, затем **Pop Stash**.

Не используйте stash как постоянное хранилище — незавершённую, но важную работу лучше сохранить в отдельной ветке.

## Отмена изменений

Отменить изменения в незакоммиченном файле:

```
git restore <файл>
```

Убрать файл из подготовленных к коммиту:

```
git restore --staged <файл>
```

Создать безопасный обратный коммит для уже опубликованного изменения:

```
git revert <commit>
```

Команды `restore`, `reset` и удаление веток могут привести к потере незакоммиченной работы. Перед их применением проверяйте `git status`.

## После слияния Pull Request

```
git switch main
git pull --ff-only
git branch -d feature/task-name
git fetch --prune
```

Удалённую ветку обычно удаляют при слиянии Pull Request через GitHub или GitLab.

## Команды для быстрой проверки

```
git status
git diff
git diff --staged
git log --oneline --graph --decorate -15
git branch --show-current
git fetch --prune
```

В редакторе аналогичная информация доступна в панелях **Source Control**, **Branches**, **History** и **Graph**. Для расширенной истории можно использовать GitLens или Git Graph.

## Правила командной работы

- Перед новой задачей обновляйте основную ветку.
    
- Одна задача — одна ветка.
    
- Не добавляйте пароли, токены, `.env` и приватные ключи.
    
- Проверяйте изменения перед коммитом.
    
- Делайте небольшие и понятные коммиты.
    
- Перед отправкой запускайте тесты и проверку стиля.
    
- Не делайте force push в общие и защищённые ветки.
    
- Не переписывайте чужую историю без согласования.
    
- Не смешивайте исправление ошибки, рефакторинг и форматирование в одном Pull Request.
    
- Если не уверены в опасной команде — сначала сохраните работу и спросите коллегу.
